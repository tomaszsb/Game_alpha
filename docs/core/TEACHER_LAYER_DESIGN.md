# Teacher Instance Layer — design spec ("deck of cards" model)

**Status:** Design approved by maintainer 2026-06-12 (interactive design session). Four external reviews same day, all approving: #1 contributed four tightenings (full-copy overrides, stable card ids, pre-baked resolved files, detours baked into the resolved graph); #2 confirmed disclosed risks, hosting question closed by measurement; #3 triaged — six structural adoptions (timestamps, reserved ownership fields, version stamps, resolver validation report, instance backups, idempotent migration + tests), draft/publish deferred, enterprise audit-trail machinery rejected at this scale; #4 (code-grounded, claims verified against the codebase) — slot-name-as-primary-key pinned, copy schema-drift validation, on-demand baking with fault isolation, instance write tokens from day one, migration dry-run CLI, safe-subset editing UI; runtime detour fallback rejected (premise disproven — cards cannot teleport in this codebase; frozen game boards make bake-time validation complete). Follow-up Q&A (2026-06-12) resolved the three remaining design questions — structure-only copy migration ("migrate structure, never meaning"), two-tier space protection (structural vs semantic feature anchors), conditionally protected path-choice topology — and added two operational invariants (atomic config writes; game creation gated on `configVersion == resolvedVersion`). **Design is converged; no open design questions remain that can be answered before code exists.** No code yet — build phases below.
**Owns:** the master-library vs per-classroom separation, the space catalog, and the permanent fix for the data-deploy gap.

## The problem this kills

The live server copies the repo's game data into its writable volume **once, on first boot**, and every later deploy leaves it alone ([server.js](../../server/server.js) `initWritableData`). That protects the maintainer's board arrangement, but it also means content fixes in the repo never reach the live game without a manual SSH merge (done by hand 2026-06-09 — the "data-deploy gap"). Root cause: `Spaces.csv` mixes **content** (titles, text, labels, narratives), **behavior** (cards, time, fees, movement), and **per-classroom customization** (`pos_x`/`pos_y`) in the same rows of the same file, so updates and customizations can only be kept by refusing one or the other.

## The model

The maintainer's chosen mental model (2026-06-12): **a deck of cards**, not a merge.

- **Master library (the stock deck)** — every space the game ships with. Owned by the repo; refreshed on the server **on every deploy, unconditionally**. Never edited in place on the server. Nothing is ever deleted from it — superseded cards just stop being used.
- **Classroom (instance)** — one teacher's table. Holds ONLY that teacher's choices: which cards are in use vs in the unused pile, tile positions, the teacher's own card copies, and detour rules. **Deploys never touch classroom data.**
- **Teacher's copy** — a teacher who wants different wording/behavior does not edit the stock card; they get a **copy** of it with their changes, played in the same slot. The stock original stays intact in the library (their unused pile).
- **Used/unused marker** — flipping it never destroys anything.

Because stock cards are only ever changed by deploys and classroom cards are only ever changed by teachers, **there is no merge step anywhere — and therefore nothing that can be lost.** The data-deploy gap is eliminated by construction, not by a smarter sync.

## Decisions (maintainer, 2026-06-12)

1. **Everything is overridable** — but via teacher copies, never via in-place edits of stock.
2. **Updates flow automatically**: every deploy refreshes the server's stock deck. Classrooms are untouched. (The previously planned "Apply latest updates" smart-merge button is obsolete — superseded by this model.)
3. **The maintainer's live edits default to classroom copies** (he wears the teacher hat in the live editor). Stock changes happen in repo sessions only, where tests pin the content. No two-way sync, no drift.
4. **Multi-teacher is in the data model from day one** (everything keyed by instance id). The sign-up/auth front door comes later (Phase 3).
5. **Board composition is locked at game start.** Catalog changes affect *new* games only; running games keep the board they started with (resolved snapshot per game).
6. **Switching a space off uses the hybrid confirm flow**: the screen computes the automatic pass-through ("Fee review will now lead to Audit"), shows the before/after path with that suggestion pre-filled, and lets the teacher confirm or pick a different detour before saving.

## Data model sketch (implementation guide, not final schema)

- **Stock**: `public/data/SOURCE_FILES` + generated `CLEAN_FILES`, exactly as today in the repo. On the server, the stock copy is refreshed from `dist` on every deploy (replaces the current first-boot-only rule). `BASELINE` and the backups mechanism stay as the safety net.
- **Instance store** (writable volume): `game-data/instances/<instanceId>/` containing one config, roughly:
  - `meta`: id, display name, created/updated timestamps, plus **reserved ownership fields for Phase 3** (owner, co-teachers, class code, visibility) — empty until then, reserved now so collaboration doesn't force a schema rework (third-review adoption, 2026-06-12)
  - `slots[space_name]`: `used` flag, `pos_x`/`pos_y`, and which card fills the slot (the stock card by default, or a teacher copy by id)
  - `teacherCopies/<copy_id>`: **complete card rows** (audit decision A — full copies, NOT field-level overrides; no inheritance logic). Each copy has a **stable id** distinct from the slot name, e.g. `fee_review_copy_1` (audit decision B — Phase 4 insertion depends on unique card ids), and records created/updated timestamps plus the stock version it was copied from, so the catalog can show "the original has been updated since you copied it" — a *hint for the teacher*, never an auto-merge.
  - `detours[space_name]`: explicit destination for switched-off spaces (saved by the hybrid confirm flow)
- **Slots vs cards**: movement targets *slots* (`space_name`); a slot is filled by exactly one card (stock or teacher copy). Pulling a card without replacement = an empty slot = a detour.
- **INVARIANT — slot names are the only space identifiers in baked files** (review #4, verified): gameplay services contain 33 hardcoded space-name checks across 8 files (e.g. [DiceRollProcessor.ts](../../src/services/DiceRollProcessor.ts) DOB final review). A teacher copy's id (`fee_review_copy_1`) exists only in the instance config for catalog/metadata purposes; in resolved data its content appears under the slot's `space_name`. Copy ids must never leak into resolved files.
- **Instance write token** (review #4, consistent with the v3.0.72 access model — "watching open, touching keyed"): every instance gets a write token at creation, same pattern as per-game tokens; instance-mutating endpoints require it (or admin) from Phase 1, so anonymous pre-auth classrooms are never hijackable and Phase 3 account linking is just attaching ownership to existing tokens.
- **INVARIANT — atomicity end to end** (Q&A resolution, 2026-06-12; strengthened by auditor #3 follow-up): per-file atomic writes alone are NOT enough — a reader assembling several files separately can still see a torn mix of old and new. Four requirements:
  1. **Atomic classroom-config replacement** — the config is replaced as one unit (simplest implementation: a *single* config file holding slots, copies, and detours, written temp → fsync → rename; a multi-file layout would need a directory-level swap instead).
  2. **Atomic resolved-output replacement** — baking writes a fresh `resolved.new/` directory and renames it into place as a unit; never regenerate resolved files in place while game-create might read them.
  3. **Version-pinned reads** — the resolver reads one immutable snapshot of the config; game creation binds to the exact resolved snapshot it read and never re-opens source files afterward; any cache of resolved output is version-keyed.
  4. **No in-place mutation** of an active config or active resolved set, ever.

  With these four (plus the `configVersion == resolvedVersion` gate), a new game starts from either the old good board or the new good board — never a torn one — which is what makes the deferred draft/publish workflow safely unnecessary at this scale.
- **Resolution** (audit decision C): the server **bakes each instance's finished board into generated files** — e.g. `game-data/instances/<instanceId>/resolved/` mirroring the CLEAN_FILES set. **Baking is on-demand, not boot-time** (review #4): regenerate when an instance is touched (config save, dashboard open, game create) and its baked version stamp doesn't match the current stock version + config version; each bake is fault-isolated so one corrupt classroom config can never block server boot or affect other classrooms. Gameplay reads them through the existing DataService → CLEAN_FILES pipeline unchanged; no runtime composition. **Each baked set carries an instance config version stamp, and every game records which version its snapshot came from** — so "why didn't this game get the latest board?" is answerable at a glance (third-review adoption). **Game creation is permitted only when the resolved set's version matches the current config version** (`configVersion == resolvedVersion`) — a half-failed bake can never seed a game (Q&A resolution, 2026-06-12; together with atomic writes this closes the realistic operational holes without a draft/publish workflow). Games belong to an instance and snapshot their resolved board at creation (decision 5).
- **Migration (Phase 1)**: diff the current live working copy against repo stock; every difference (positions, any text drift) becomes classroom #1's config. Nothing the maintainer has arranged is lost. After migration, the server's stock starts auto-refreshing.
- **Editor mapping**: board drag-save ([saveBoardPosition.ts](../../src/components/board/saveBoardPosition.ts)) and the content editor ([DataEditor.tsx](../../src/components/editor/DataEditor.tsx)) write to the *instance*, not stock (decision 3). The `save-source-files` endpoint's role shrinks accordingly.

## Detour semantics (the catalog's hard part)

- **Detours are not a runtime feature** (audit decision D): the resolver bakes them into the final movement graph at config-save time. A running game never knows what was disabled, detoured, or original — MovementService only ever sees a finished board where, say, Fee review leads to Audit.
- **The resolver's input is the final slot graph *after* teacher-copy substitution** — if a copy fills a slot and changes movement, the copy's movement governs, not the stock original's. Its output is the baked files **plus a validation report** (cycles, unreachable spaces, fan-in from multiple off-spaces converging on one target, chains crossing protected spaces) — the same report the hybrid confirm screen displays (third-review adoption). Loops are save-time errors shown to the teacher, never silently auto-resolved (review #4's "detour to nearest safe hub" rejected — hides the mistake from the person best placed to fix it).
- **INVARIANT — a resolved board never references an inactive space, in ANY file** (review #4, generalized): space names appear in 10 of the 12 CLEAN files (dice outcomes, space effects, tooltips…), not just MOVEMENT.csv. Bake-time validation checks them all. Verified 2026-06-12: cards CANNOT teleport players (CARDS_EXPANDED `target` column holds only player-targeting values, zero space names), and game boards are frozen at creation (decision 5) — so bake-time validation is *complete* and review #4's proposed runtime detour fallback is unnecessary dead weight; rejected.
- **Schema-drift validation** (review #4 — a real gap in the full-copy model): stock gains new columns over time (e.g. `has_final_review_gate`); a teacher copy is frozen at the structure it was copied with. The validation report checks every copy against the current stock schema and flags structurally outdated copies in the catalog. **Structure aligns automatically, meaning never does** (Q&A + auditor #4, in agreement, 2026-06-12): at bake time, copies missing newly added columns get them filled from the current stock row — pure schema migration, recorded in the validation report, safe to automate. Content/behavior differences are NEVER reconciled automatically — no three-way compare, no merge engine; the staleness hint ("the original has been updated since you copied it") invites a teacher-initiated review, and that is the only path by which a copy's meaning changes.
- Pass-through suggestion = follow the switched-off space's own outgoing movement until landing on a used space. Chains of off spaces resolve transitively.
- Validation at save time (all picking happens before games start — decision 5): cycles, dead ends, and unreachable boards are errors shown to the teacher, not runtime surprises.
- **Protection is two-tier, rolled out gradually** (Q&A + auditor #4 reconciled, 2026-06-12): **structural spaces** (start, end, resume hubs) can never be switched off. **Semantic feature anchors** — spaces an engine feature depends on (e.g. DOB final review → approval mechanic; cf. the 33 hardcoded space references) — start out **protected too when Phase 2 ships** (auditor #4's position: naive degradation cascades — disable Plan Exam while the Final Review gate still expects approval and a player is permanently trapped). Then features **graduate to disableable one at a time** (the Q&A position: a permanent protect-everything list swallows half the board and defeats the catalog): a feature graduates only after it (a) declares its required spaces and dependency cascade, (b) shows the consequence at switch-off time ("the approval mechanic will be off in this classroom — continue?") and bakes a board with the feature *cleanly absent*, and (c) **passes a ghost-batch graduation gate** (auditor #4, using the existing Ghost Player suite): ~100 simulated games on a classroom with the feature off, asserting no runtime errors, no infinite loops, and a stable game-completion rate. Affected test suites run under both modes (capability matrix, `describe.each`).
- **Path-choice topology is conditionally protected** (Q&A resolution, 2026-06-12 — flagged as the most dangerous issue in the spec, ahead of card insertion): the resolver traces every player-facing choice to its eventual destinations after detours. If disabling a space collapses two choices into one, removes a choice target, or orphans a `path_choice_memory_key`, the save is **rejected** with an explanation (e.g. "Disabling Space X invalidates choice Y — adjust the detour target"). Spaces are protected only *while* they serve a choice structure, not globally. Rewriting PATH_CHOICE_RULES during the bake was considered and rejected (that's building a compiler). The failure mode this guards against is silent intent corruption — player picks the Left path, the game quietly delivers Right — which is worse than any crash. *(Two auditors reached this exact conclusion independently, naming the same failure mode — treated as settled.)*
- Games only ever read resolved movement — a running game never sees a missing space.
- Known complexity to handle in implementation: dice-based movement rows, path-choice spaces/lock points, `MOVEMENT.csv` conditions. The resolver must operate on the generated CLEAN movement data, not just `Spaces.csv` columns.

## Build order

1. **Foundation** — the library/instance split + migration of the live board into classroom #1 + stock auto-refresh on deploy. Invisible to players; kills the data-loss risk permanently. *(Prerequisite for everything else.)* Migration is one-time but **idempotent and verifiable** (safe to re-run, detects a partial run), with a **dry-run CLI** (`npm run migrate:check`, review #4) that prints exactly what live-board differences would become classroom #1's config before anything is written. Phase 1 also includes: on-demand fault-isolated baking, instance write tokens, schema validation in the resolver, and per-instance write serialization (drag-saves debounced/queued per instance so rapid edits can't race on the filesystem). Classroom configs join the existing backup/restore mechanism, so a bad teacher edit is a one-step rollback. Baking + migration ship with targeted automated tests (deterministic output, snapshot stability across deploys; resolver validation tests — cycles, unreachable spaces, protected-space switch-offs — join in Phase 2).
2. **Teacher catalog screen** — browse the deck, switch on/off (hybrid confirm flow), swap in copies, arrange the board. **Editing UI starts with a safe field subset** (title, narrative text, fees) with per-field "differs from stock" highlighting and per-field revert — the model stores full copies underneath (decision 1 unchanged), the UI opens doors gradually (review #4). Also ships the "update my copy's structure" helper for schema-drifted copies.
3. **Multi-teacher front door** — DESIGN SETTLED 2026-06-12 (maintainer session, while Phases 1–2 awaited deploy):
   - **Full teacher accounts, admin-mediated.** Only the maintainer creates classrooms, and he creates the teacher's account (username + password) with them — no self-signup, and **no email infrastructure**: password resets are admin-mediated too (the same person who hands out classrooms resets passwords). Passwords scrypt-hashed in the writable volume; login yields a session token (existing token patterns).
     - **AMENDED 2026-06-14 (Phase 3 polish, after live use):** classroom *creation* is no longer admin-only — a logged-in teacher creates their own classrooms (`POST /api/instances`, session-authed, room auto-owned; id generated from the name). Teachers and admin can both delete (teacher: own rooms; admin: any; `classroom-1` never deletable). **Account creation stays admin-only** (still no self-signup/email). The maintainer reversed the "admin creates classrooms" half after using it: making teachers wait on the admin for every room was the wrong friction (fb:517bf765).
   - **Ownership binds via the reserved field**: `meta.owner` = account id; a teacher's session authorizes writes to owned classrooms. Per-instance write tokens remain the underlying mechanism (a session is just a key to them).
   - **Games belong to a classroom**: a game created from a teacher's session records that instanceId; players type the game code exactly as today and the client loads that classroom's baked board (per-instance serving, e.g. `/data/i/<instanceId>/…`). Zero change to the player experience.
   - **classroom-1 stays the public face**: plain visitors and instance-less games get today's behavior unchanged.
   - Work items: accounts store + login/reset endpoints, ownership binding in the mutation guard, instanceId on games + per-instance data routing in client + server, login/classroom-picker UI (Classroom Setup drops its hardcoded classroom-1), admin create-classroom+account tool.
4. **Card insertion** — "replace one card with several" / brand-new teacher-authored spaces inserted into the path. Most invasive (rewires movement); deliberately last. **Audit note: this is the project's biggest future risk** — it shifts the model from *spaces are selected* to *spaces are authored*, which hardens path validation, movement generation, layout, and snapshotting all at once. Do not begin designing it until Phases 1–3 have been running successfully.

## Explicitly deferred / open questions

- ~~Teacher auth model for Phase 3~~ — RESOLVED 2026-06-12: full accounts, admin-mediated (see build order item 3).
- ~~Catalog UI shape~~ — RESOLVED 2026-06-12: separate teacher screen (Classroom Setup, shipped v3.0.76).
- **Draft vs published classroom config** — deferred to Phase 2 design; deferral confirmed by auditors #3 and #4 given the atomicity invariants. The accepted residual (auditor #4): a teacher who saves *halfway through a rearrangement* produces a valid-but-unfinished board, and a game started that second snapshots it — no atomicity scheme prevents this because every save is internally consistent. Mitigation at this scale: a catalog UI hint ("you are editing the live board") and nothing more. If real classrooms hit it, a publish step is an additive feature, not a redesign.
- **Duplicate a classroom** ("clone for next term") — cheap under this model (copy one config folder); Phase 3 nice-to-have.
- **Concurrent edits** (same classroom open in two tabs → last save wins) — known and accepted for the single-teacher phases; revisit at Phase 3 (Q&A, 2026-06-12). Per-instance write serialization already prevents file corruption; this is only about lost intent.
- **Considered and REJECTED at this scale** (third review, 2026-06-12): per-edit audit trails with who/when/rationale notes (compliance machinery — solo maintainer + small-school scale; backups + timestamps cover recovery and support), and making teacher copies immutable once a game references them (redundant — game snapshots already freeze the whole board, a stronger guarantee).
- Stock content versioning/history (BASELINE + backups are considered sufficient for now).
- Hosting limits — **largely closed by measurement (2026-06-12):** one complete baked data set is ~253 KB CLEAN + ~39 KB SOURCE, so ~300 KB per classroom — 1,000 classrooms ≈ 300 MB of disk, trivial for the Unraid volume. Nothing is held in memory per instance (resolved files are served statically; games snapshot their own board). At the project's stated scale (schools = dozens-to-hundreds, per BETA_PLAN_V3 scope), this is a non-issue. Optional later optimization: instance-invariant files (e.g. GLOSSARY.csv, ~100 KB — pure shared content) could be served from stock instead of being duplicated per instance.

## The problem this kills

The live server copies the repo's game data into its writable volume **once, on first boot**, and every later deploy leaves it alone ([server.js](../../server/server.js) `initWritableData`). That protects the maintainer's board arrangement, but it also means content fixes in the repo never reach the live game without a manual SSH merge (done by hand 2026-06-09 — the "data-deploy gap"). Root cause: `Spaces.csv` mixes **content** (titles, text, labels, narratives), **behavior** (cards, time, fees, movement), and **per-classroom customization** (`pos_x`/`pos_y`) in the same rows of the same file, so updates and customizations can only be kept by refusing one or the other.

## The model

The maintainer's chosen mental model (2026-06-12): **a deck of cards**, not a merge.

- **Master library (the stock deck)** — every space the game ships with. Owned by the repo; refreshed on the server **on every deploy, unconditionally**. Never edited in place on the server. Nothing is ever deleted from it — superseded cards just stop being used.
- **Classroom (instance)** — one teacher's table. Holds ONLY that teacher's choices: which cards are in use vs in the unused pile, tile positions, the teacher's own card copies, and detour rules. **Deploys never touch classroom data.**
- **Teacher's copy** — a teacher who wants different wording/behavior does not edit the stock card; they get a **copy** of it with their changes, played in the same slot. The stock original stays intact in the library (their unused pile).
- **Used/unused marker** — flipping it never destroys anything.

Because stock cards are only ever changed by deploys and classroom cards are only ever changed by teachers, **there is no merge step anywhere — and therefore nothing that can be lost.** The data-deploy gap is eliminated by construction, not by a smarter sync.

## Decisions (maintainer, 2026-06-12)

1. **Everything is overridable** — but via teacher copies, never via in-place edits of stock.
2. **Updates flow automatically**: every deploy refreshes the server's stock deck. Classrooms are untouched. (The previously planned "Apply latest updates" smart-merge button is obsolete — superseded by this model.)
3. **The maintainer's live edits default to classroom copies** (he wears the teacher hat in the live editor). Stock changes happen in repo sessions only, where tests pin the content. No two-way sync, no drift.
4. **Multi-teacher is in the data model from day one** (everything keyed by instance id). The sign-up/auth front door comes later (Phase 3).
5. **Board composition is locked at game start.** Catalog changes affect *new* games only; running games keep the board they started with (resolved snapshot per game).
6. **Switching a space off uses the hybrid confirm flow**: the screen computes the automatic pass-through ("Fee review will now lead to Audit"), shows the before/after path with that suggestion pre-filled, and lets the teacher confirm or pick a different detour before saving.

## Data model sketch (implementation guide, not final schema)

- **Stock**: `public/data/SOURCE_FILES` + generated `CLEAN_FILES`, exactly as today in the repo. On the server, the stock copy is refreshed from `dist` on every deploy (replaces the current first-boot-only rule). `BASELINE` and the backups mechanism stay as the safety net.
- **Instance store** (writable volume): `game-data/instances/<instanceId>/` containing one config, roughly:
  - `meta`: id, display name, created/updated timestamps, plus **reserved ownership fields for Phase 3** (owner, co-teachers, class code, visibility) — empty until then, reserved now so collaboration doesn't force a schema rework (third-review adoption, 2026-06-12)
  - `slots[space_name]`: `used` flag, `pos_x`/`pos_y`, and which card fills the slot (the stock card by default, or a teacher copy by id)
  - `teacherCopies/<copy_id>`: **complete card rows** (audit decision A — full copies, NOT field-level overrides; no inheritance logic). Each copy has a **stable id** distinct from the slot name, e.g. `fee_review_copy_1` (audit decision B — Phase 4 insertion depends on unique card ids), and records created/updated timestamps plus the stock version it was copied from, so the catalog can show "the original has been updated since you copied it" — a *hint for the teacher*, never an auto-merge.
  - `detours[space_name]`: explicit destination for switched-off spaces (saved by the hybrid confirm flow)
- **Slots vs cards**: movement targets *slots* (`space_name`); a slot is filled by exactly one card (stock or teacher copy). Pulling a card without replacement = an empty slot = a detour.
- **INVARIANT — slot names are the only space identifiers in baked files** (review #4, verified): gameplay services contain 33 hardcoded space-name checks across 8 files (e.g. [DiceRollProcessor.ts](../../src/services/DiceRollProcessor.ts) DOB final review). A teacher copy's id (`fee_review_copy_1`) exists only in the instance config for catalog/metadata purposes; in resolved data its content appears under the slot's `space_name`. Copy ids must never leak into resolved files.
- **Instance write token** (review #4, consistent with the v3.0.72 access model — "watching open, touching keyed"): every instance gets a write token at creation, same pattern as per-game tokens; instance-mutating endpoints require it (or admin) from Phase 1, so anonymous pre-auth classrooms are never hijackable and Phase 3 account linking is just attaching ownership to existing tokens.
- **INVARIANT — atomicity end to end** (Q&A resolution, 2026-06-12; strengthened by auditor #3 follow-up): per-file atomic writes alone are NOT enough — a reader assembling several files separately can still see a torn mix of old and new. Four requirements:
  1. **Atomic classroom-config replacement** — the config is replaced as one unit (simplest implementation: a *single* config file holding slots, copies, and detours, written temp → fsync → rename; a multi-file layout would need a directory-level swap instead). **Keep single-file through Phases 1–3, but with an internally-sectioned schema** (audit round 4, pushing back on the "split into a config directory now" proposal): top-level keys `slots` / `copies` / `detours` / `insertions` / `meta` are kept as cleanly separable sections. At this scale a config is kilobytes and a debounced drag-save rewriting it is genuinely free, so a directory split now is complexity for a scalability problem we don't have. But *if* Phase 4 insertions ever bloat the file, the sectioned schema makes the directory-level-swap split **mechanical, not a redesign** — the escape hatch is banked without paying for it early.
  2. **Atomic resolved-output replacement** — baking writes a fresh `resolved.new/` directory and renames it into place as a unit; never regenerate resolved files in place while game-create might read them.
  3. **Version-pinned reads** — the resolver reads one immutable snapshot of the config; game creation binds to the exact resolved snapshot it read and never re-opens source files afterward; any cache of resolved output is version-keyed.
  4. **No in-place mutation** of an active config or active resolved set, ever.

  With these four (plus the `configVersion == resolvedVersion` gate), a new game starts from either the old good board or the new good board — never a torn one — which is what makes the deferred draft/publish workflow safely unnecessary at this scale.
- **Resolution** (audit decision C): the server **bakes each instance's finished board into generated files** — e.g. `game-data/instances/<instanceId>/resolved/` mirroring the CLEAN_FILES set. **Baking is on-demand, not boot-time** (review #4): regenerate when an instance is touched (config save, dashboard open, game create) and its baked version stamp doesn't match the current stock version + config version; each bake is fault-isolated so one corrupt classroom config can never block server boot or affect other classrooms. Gameplay reads them through the existing DataService → CLEAN_FILES pipeline unchanged; no runtime composition. **Each baked set carries an instance config version stamp, and every game records which version its snapshot came from** — so "why didn't this game get the latest board?" is answerable at a glance (third-review adoption). **Game creation is permitted only when the resolved set's version matches the current config version** (`configVersion == resolvedVersion`) — a half-failed bake can never seed a game (Q&A resolution, 2026-06-12; together with atomic writes this closes the realistic operational holes without a draft/publish workflow). Games belong to an instance and snapshot their resolved board at creation (decision 5).
- **Migration (Phase 1)**: diff the current live working copy against repo stock; every difference (positions, any text drift) becomes classroom #1's config. Nothing the maintainer has arranged is lost. After migration, the server's stock starts auto-refreshing.
- **Editor mapping**: board drag-save ([saveBoardPosition.ts](../../src/components/board/saveBoardPosition.ts)) and the content editor ([DataEditor.tsx](../../src/components/editor/DataEditor.tsx)) write to the *instance*, not stock (decision 3). The `save-source-files` endpoint's role shrinks accordingly.

## Detour semantics (the catalog's hard part)

- **Detours are not a runtime feature** (audit decision D): the resolver bakes them into the final movement graph at config-save time. A running game never knows what was disabled, detoured, or original — MovementService only ever sees a finished board where, say, Fee review leads to Audit.
- **The resolver's input is the final slot graph *after* teacher-copy substitution** — if a copy fills a slot and changes movement, the copy's movement governs, not the stock original's. Its output is the baked files **plus a validation report** (cycles, unreachable spaces, fan-in from multiple off-spaces converging on one target, chains crossing protected spaces) — the same report the hybrid confirm screen displays (third-review adoption). Loops are save-time errors shown to the teacher, never silently auto-resolved (review #4's "detour to nearest safe hub" rejected — hides the mistake from the person best placed to fix it).
- **INVARIANT — a resolved board never references an inactive space, in ANY file** (review #4, generalized): space names appear in 10 of the 12 CLEAN files (dice outcomes, space effects, tooltips…), not just MOVEMENT.csv. Bake-time validation checks them all. Verified 2026-06-12: cards CANNOT teleport players (CARDS_EXPANDED `target` column holds only player-targeting values, zero space names), and game boards are frozen at creation (decision 5) — so bake-time validation is *complete* and review #4's proposed runtime detour fallback is unnecessary dead weight; rejected.
- **Schema-drift validation** (review #4 — a real gap in the full-copy model): stock gains new columns over time (e.g. `has_final_review_gate`); a teacher copy is frozen at the structure it was copied with. The validation report checks every copy against the current stock schema and flags structurally outdated copies in the catalog. **Structure aligns automatically, meaning never does** (Q&A + auditor #4, in agreement, 2026-06-12): at bake time, copies missing newly added columns get them filled from the current stock row — pure schema migration, recorded in the validation report, safe to automate. Content/behavior differences are NEVER reconciled automatically — no three-way compare, no merge engine; the staleness hint ("the original has been updated since you copied it") invites a teacher-initiated review, and that is the only path by which a copy's meaning changes.
- Pass-through suggestion = follow the switched-off space's own outgoing movement until landing on a used space. Chains of off spaces resolve transitively.
- Validation at save time (all picking happens before games start — decision 5): cycles, dead ends, and unreachable boards are errors shown to the teacher, not runtime surprises.
- **Protection is two-tier, rolled out gradually** (Q&A + auditor #4 reconciled, 2026-06-12): **structural spaces** (start, end, resume hubs) can never be switched off. **Semantic feature anchors** — spaces an engine feature depends on (e.g. DOB final review → approval mechanic; cf. the 33 hardcoded space references) — start out **protected too when Phase 2 ships** (auditor #4's position: naive degradation cascades — disable Plan Exam while the Final Review gate still expects approval and a player is permanently trapped). Then features **graduate to disableable one at a time** (the Q&A position: a permanent protect-everything list swallows half the board and defeats the catalog): a feature graduates only after it (a) declares its required spaces and dependency cascade, (b) shows the consequence at switch-off time ("the approval mechanic will be off in this classroom — continue?") and bakes a board with the feature *cleanly absent*, and (c) **passes a ghost-batch graduation gate** (auditor #4, using the existing Ghost Player suite): ~100 simulated games on a classroom with the feature off, asserting no runtime errors, no infinite loops, and a stable game-completion rate. Affected test suites run under both modes (capability matrix, `describe.each`).
- **Path-choice topology is conditionally protected** (Q&A resolution, 2026-06-12 — flagged as the most dangerous issue in the spec, ahead of card insertion): the resolver traces every player-facing choice to its eventual destinations after detours. If disabling a space collapses two choices into one, removes a choice target, or orphans a `path_choice_memory_key`, the save is **rejected** with an explanation (e.g. "Disabling Space X invalidates choice Y — adjust the detour target"). Spaces are protected only *while* they serve a choice structure, not globally. Rewriting PATH_CHOICE_RULES during the bake was considered and rejected (that's building a compiler). The failure mode this guards against is silent intent corruption — player picks the Left path, the game quietly delivers Right — which is worse than any crash. *(Two auditors reached this exact conclusion independently, naming the same failure mode — treated as settled.)*
- Games only ever read resolved movement — a running game never sees a missing space.
- Known complexity to handle in implementation: dice-based movement rows, path-choice spaces/lock points, `MOVEMENT.csv` conditions. The resolver must operate on the generated CLEAN movement data, not just `Spaces.csv` columns.

## Build order

1. **Foundation** — the library/instance split + migration of the live board into classroom #1 + stock auto-refresh on deploy. Invisible to players; kills the data-loss risk permanently. *(Prerequisite for everything else.)* Migration is one-time but **idempotent and verifiable** (safe to re-run, detects a partial run), with a **dry-run CLI** (`npm run migrate:check`, review #4) that prints exactly what live-board differences would become classroom #1's config before anything is written. Phase 1 also includes: on-demand fault-isolated baking, instance write tokens, schema validation in the resolver, and per-instance write serialization (drag-saves debounced/queued per instance so rapid edits can't race on the filesystem). Classroom configs join the existing backup/restore mechanism, so a bad teacher edit is a one-step rollback. Baking + migration ship with targeted automated tests (deterministic output, snapshot stability across deploys; resolver validation tests — cycles, unreachable spaces, protected-space switch-offs — join in Phase 2). **Also in Phase 1 (audit round 3, CORE-4): make game snapshots self-contained** — a created game carries its own resolved board and stops re-fetching `/data/i/<id>/`, closing the divergence from decision 5 and decoupling deletion/DR/replay from classroom storage. Pulled forward because Phase 1 already touches the resolver, game creation, and versioning — the cheapest time to do it.
2. **Teacher catalog screen** — browse the deck, switch on/off (hybrid confirm flow), swap in copies, arrange the board. **Editing UI starts with a safe field subset** (title, narrative text, fees) with per-field "differs from stock" highlighting and per-field revert — the model stores full copies underneath (decision 1 unchanged), the UI opens doors gradually (review #4). Also ships the "update my copy's structure" helper for schema-drifted copies.
3. **Multi-teacher front door** — DESIGN SETTLED 2026-06-12 (maintainer session, while Phases 1–2 awaited deploy):
   - **Full teacher accounts, admin-mediated.** Only the maintainer creates classrooms, and he creates the teacher's account (username + password) with them — no self-signup, and **no email infrastructure**: password resets are admin-mediated too (the same person who hands out classrooms resets passwords). Passwords scrypt-hashed in the writable volume; login yields a session token (existing token patterns).
     - **AMENDED 2026-06-14 (Phase 3 polish, after live use):** classroom *creation* is no longer admin-only — a logged-in teacher creates their own classrooms (`POST /api/instances`, session-authed, room auto-owned; id generated from the name). Teachers and admin can both delete (teacher: own rooms; admin: any; `classroom-1` never deletable). **Account creation stays admin-only** (still no self-signup/email). The maintainer reversed the "admin creates classrooms" half after using it: making teachers wait on the admin for every room was the wrong friction (fb:517bf765).
   - **Ownership binds via the reserved field**: `meta.owner` = account id; a teacher's session authorizes writes to owned classrooms. Per-instance write tokens remain the underlying mechanism (a session is just a key to them).
   - **Games belong to a classroom**: a game created from a teacher's session records that instanceId; players type the game code exactly as today and the client loads that classroom's baked board (per-instance serving, e.g. `/data/i/<instanceId>/…`). Zero change to the player experience.
   - **classroom-1 stays the public face**: plain visitors and instance-less games get today's behavior unchanged.
   - Work items: accounts store + login/reset endpoints, ownership binding in the mutation guard, instanceId on games + per-instance data routing in client + server, login/classroom-picker UI (Classroom Setup drops its hardcoded classroom-1), admin create-classroom+account tool.
4. **Card insertion** — "replace one card with several" / brand-new teacher-authored spaces inserted into the path. Most invasive (rewires movement); deliberately last. **Audit note: this is the project's biggest future risk** — it shifts the model from *spaces are selected* to *spaces are authored*, which hardens path validation, movement generation, layout, and snapshotting all at once. Do not begin designing it until Phases 1–3 have been running successfully. **Design pass drafted 2026-06-15 — see [Phase 4 design](#phase-4-design--card-insertion-full-space-editor-target-tiered-delivery) below.** Maintainer's scope call (2026-06-15): **full space editor is the target capability** (an authored space may eventually do anything a stock space can). Delivered in four tiers (4a–4d) so each invariant the spec closed is re-hardened deliberately, not all at once.

### The model shift

Phases 1–3 rest on one invariant: **every slot name is a stock space name**, and spaces are *selected*, never created. A teacher copy refills an existing slot under its existing `space_name`, so the engine's per-space behavior (Workstream 6 data columns + the residual name-literal checks) stays valid by construction. Phase 4 lets a teacher **author a brand-new space and splice it into the path** — a `space_name` that does not exist in stock and is referenced by no engine code. That is safe *only* for behavior the engine reads off data columns; it is unsafe for any behavior the engine keys to a literal stock name. The pre-work for Phase 4 is therefore an audit of which behaviors are which.

> **The architectural cliff (audit round 2, 2026-06-15).** Phase 4 is the point where **classroom authors become content authors** — the system crosses from a *configuration system* (select + copy stock) to a *user-generated game engine* (author movement, effects, conditions). Every invariant assumed by Phases 1–3 was proven against *stock* content; authored spaces introduce behaviors that have never existed in stock, so **every Phase 1–3 invariant must be explicitly revalidated against authored content before its tier ships** — not assumed to carry over. The tier ladder exists precisely to make that revalidation incremental.

### Tier ladder

Each tier ships behind the same **ghost-batch graduation gate** Phase 2 uses for feature switch-off, and depends on the new **LOOP-detection gate** (TODO, post-v3.0.80) landing first — authored insertions are precisely the change that can seed a silent unwinnable loop a green gate would otherwise absorb as a TURN_CAP loss.

| Tier | An authored space can… | Re-hardens / requires | Bucket-C lift | Status |
|---|---|---|---|---|
| **4a** | Insert a **narrative pass-through** on a single `fixed` edge (story text + optional flat time/money) | insertion topology (simple splice), authored-id namespace, layout, snapshot id-stability | none | **on roadmap** |
| **4b** | Splice into a **specific edge** of a `choice`/`dice` space; add **palette mechanics** (flat fees, card draws, dice outcomes) | edge-targeted splice, DICE_OUTCOMES authoring, fee-formula validation | `fee_category` | **on roadmap** |
| **4c** | Author spaces with **engine features** (approval gates, etc.) | the name-literal subset of the engine (ApprovalService); per-feature ghost graduation gate | ApprovalService → CSV | **CUT** (audit round 3) |
| **4d** | Author **new branching / choice topology** | PATH_CHOICE_RULES + `path_choice_memory_key` generation — the spec's #1 named danger | none (generative) | **CUT** (audit round 3) |

**The content/engine boundary (audit round 3, 2026-06-15).** Phase 4 is **4a + 4b only** — *content authoring*. Tiers 4c and 4d are **cut from the roadmap** until a real classroom demands them, because they are *game-engine authoring*, not content: a new approval gate or a new branch is a new state machine (new conditions, progression rules, UI semantics, validation), which is a different product. A teacher who wants different wording / fees / narrative / placement / sequencing already gets all of it from stock spaces + copies + insertion + detours. The line: **4a/4b let teachers author content; 4c/4d would let them author the engine.** This single cut removes the ApprovalService lift (the deepest name-literal coupling) and the PATH_CHOICE_RULES generator (the spec's #1 named danger) from the plan entirely — the largest risk reduction available. Re-open only on a concrete request that 4a/4b provably can't satisfy.

### Insertion topology (the core movement rewire)

"Insert N between A and B" is unambiguous only when A→B is a single `fixed` edge: the resolver repoints A's outgoing edge to N and gives N a single `fixed` edge to B. The hard cases, deferred up the ladder:
- **A has multiple outgoing edges** (`choice`/`dice`): the teacher must select the *specific edge* to splice, not the space. The catalog UI targets an edge (A→B), not a node. (Tier 4b.)
- **A is a path-choice lock point**: splicing after it must preserve the `path_choice_memory_key`; collapsing or orphaning a choice is a hard save-time rejection (existing resolver invariant). (Interacts with 4d.)
- **N is itself a `choice` space** (the teacher authors new branching): this is tier 4d — generating valid PATH_CHOICE_RULES rows + memory keys from a teacher's edits, which the spec calls more dangerous than insertion itself.

The resolver's existing detour/validation machinery already operates on the baked CLEAN movement graph and already reports cycles / unreachable / orphaned-choice / protected-space crossings. **Insertion is the additive twin of detour:** detour removes a node and reroutes through it; insertion adds a node and reroutes around it. Both bake into the final graph at config-save time; a running game never sees the authored-vs-stock distinction. The same validation report covers both.

### Authored-space id namespace

Authored spaces need ids in the **same namespace as slots** (movement targets slot names), distinct from teacher-copy ids, and collision-proof against future stock additions. Proposal: reserved prefix `auth-<instanceId>-<n>`, validated by the existing `^[a-z0-9][a-z0-9-]*$` instance regex, never emitted by stock. The Phase 1–3 invariant "copy ids never leak into resolved files" is *extended*, not broken: copy ids still never appear in resolved files, but authored ids **do** appear there as first-class slot names (they are real spaces, not metadata).

**internalId + displayName, both preserved through baking** (audit round 4). The `auth-<instanceId>-<n>` id is debug-hostile on its own — `Player landed on auth-classroom-3-42` is unreadable in logs and feedback reports. Every authored space carries a human `displayName` alongside its internal id, and **both** survive into the baked resolved set. This rides the existing `display_label_override` mechanism (v3.0.68 — the per-space label the board and panel already read), so it's not new machinery: the internal id is the movement key, `display_label_override` is the human name, and logs/feedback should surface the latter. The internal id stays stable forever (it's the movement target); the displayName is freely editable.

### Layout & snapshot (the cheap ones)

A new tile needs `pos_x/pos_y` with no stock default. Auto-place adjacent to the spliced edge's midpoint, then let the teacher drag it (reuse the per-instance position flow). Snapshotting already freezes the resolved board per game; the only new requirement is authored-id stability across re-bakes (guaranteed by the persisted `<n>` counter in the instance config).

### Decisions locked (audit round 3, 2026-06-15)

The open questions from round 2 are resolved:

- **Insertion targeting → edge-keyed, locked.** The config stores `insertions[]` keyed by the edge `(A, B)`, never by exit ordinal. Rationale: the resolver is already graph-oriented, so the config should be too; edge references survive a space later gaining new exits, whereas "exit #2" references silently shift. Validators already operate on edges. This is locked now because it's expensive to migrate later.
- **Multi-card replace → composite primitive, not first-class chains.** "Replace one card with several" is N sequential `fixed` inserts, not a `Chain { id, children, lifecycle }` object. Teachers think "insert Environmental Review, insert Community Hearing," not "create a review chain." First-class chains would force deletion/movement/UI/validation semantics before chains are proven to be how teachers reason. Let chains *emerge from composition*; promote to first-class only if real usage patterns demand it.
- **ApprovalService lift → removed from scope.** Was a 4c blocker; 4c is cut, so the deepest name-literal coupling stays exactly as-is. (If 4c is ever re-opened, revisit "per-space columns vs a separate `APPROVAL_RULES.csv`" then.)

**Residual genuinely-open item:** the ghost gate must still validate **authored-content boards** (4a/4b) for the LOOP failure mode — an authored insertion can seed an unwinnable cycle. But because 4a/4b add no engine *features* (only content), there is **no feature-on/off capability matrix** to explode the gate runtime — the round-2 worry about `describe.each` matrix cost evaporates with 4c/4d cut. The gate change needed is the LOOP-detection classifier (already tracked in TODO), run against a few authored-insertion fixtures, not a combinatorial matrix.

**Ghost gate certifies structure, not balance** (audit round 4; reaffirms a hard-won codebase lesson — CLAUDE.md "ghost gate catches crashes, not soft-locks" and "win-rate is secondary/easily polluted"). The graduation gate's certified claim is exactly three things: **no crashes, no loops, completion is possible.** It explicitly does **not** certify that the game stays *balanced* — a board with a feature disabled (or a flat authored insertion) can be wildly easier/harder and still pass, correctly. Any spec language that reads as "ghost batch proves the game is still good" is wrong and should be read as "ghost batch proves the game still *runs to completion without crashing or looping*." Balance is a human playtest judgment, never a gate assertion.

## Operational architecture (audit round 2 — 2026-06-15)

External review ("auditor #5") surfaced second-order risks — internally consistent design that could still fail operationally, economically, or as the system evolves. Three are architecture-blocking (cheap now, brutal to retrofit once real games exist) and are **resolved here**; the rest are documented with a position and deferred. Two cross-cutting invariants are promoted to first-class.

### CORE-1 — Version lineage model (resolved)

The spec stamped versions at every layer but never defined their *relationship*, so a bug report ("why did this game show fee $500 instead of $750?") would require archaeology across five independent version numbers. The lineage is now an explicit nested chain:

```
Game
 └─ snapshot lineage triple { resolvedVersion, configVersion, stockVersion }   ← recorded at game creation
      └─ resolved set    (baked output, carries the same triple)
           └─ instance config  (configVersion, bumped every save)
                └─ stock         (stockVersion, bumped on deploy when stock content changes)

per slot in the resolved set:
   filled by → stock card @ stockVersion   OR   teacher copy (copyId, copiedFromStockVersion)
```

**Rules:**
- Each baked resolved set carries the full **lineage triple** `{ resolvedVersion, configVersion, stockVersion }`, not just `resolvedVersion`.
- Each game records that triple at creation (extends decision 5's "records which version its snapshot came from").
- Each teacher copy records `copiedFromStockVersion` **and `copiedFromStockRowHash`** (audit round 4) — a checksum of the exact stock row at copy time. The version alone is insufficient in *this* codebase: the data-deploy gap means the maintainer can edit a live stock space **without a version bump or deploy**, so `copiedFromStockVersion: 12` can point at two different "v12" rows. The row hash makes drift detection exact and version-independent — the staleness hint fires on `currentStockRowHash !== copiedFromStockRowHash`, not on a version compare. Each resolved slot records whether it was filled by stock or a copy, and which.
- **Debug walk** (no archaeology): game triple → its resolved set → the slot in question → the card that filled it (stock@version or copy@copiedFrom) → the frozen value. One deterministic chain answers "where did this number come from."

This is metadata only — no new mechanism, no per-edit audit trail (still rejected at this scale, see deferred list). It just makes the existing version stamps *navigable*.

### CORE-2 — Recovery & "last known good" (resolved; merges auditor #2 + #9)

The atomicity invariants (atomic config replacement, atomic resolved swap, version-pinned reads, no in-place mutation) already prevent *torn* state. What was missing: an explicit **last-known-good** model and a rule for **unreadable** (not merely stale) state. Per instance, four pointers:

```
currentConfigVersion        lastKnownGoodConfigVersion
currentResolvedVersion      lastKnownGoodResolvedVersion
```

**Rules:**
- **R1 — validated-before-active.** A config becomes `current` only after it parses *and* passes resolver validation. A write that fails either is rejected; the previous `current` stays. `lastKnownGood*` advances only on a fully validated bake-and-swap.
- **R2 — degraded mode on unreadable config.** If the active config can't be read (disk corruption, interrupted edit, partial restore, future schema bug), the instance enters **degraded mode**: it keeps serving `lastKnownGoodResolved` (immutable on disk), permits new-game creation **from the last-known-good board** (a classroom is never bricked), blocks *edits* until repaired, and surfaces a repair prompt. The bad file is preserved as `config.corrupt.<ts>` for forensics — **never auto-deleted**.
- **R3 — bake never strands.** Baking writes `resolved.new`, validates, atomic-renames into place; on failure it keeps the previous resolved set. There is never zero resolved sets on disk.
- **R4 — invariant: never destroy the last working state.** Every replacement is preceded by a validated successor. (Promoted to invariant — see below.)

In-flight games are unaffected by any of this (they hold their own snapshot, CORE-1).

### CORE-3 — Classroom deletion & game retention (resolved)

First, the philosophy asymmetry the auditor correctly flagged as an internal contradiction: **"nothing is ever deleted" applies to the stock library (cards are immortal), NOT to classrooms.** Stated explicitly to end the ambiguity:

> **Cards are immortal; classrooms are mortal.** Stock cards are never deleted (superseded cards just go unused). Classrooms *can* be removed (Phase 3 already grants teacher/admin delete; `classroom-1` is never deletable).

**Decision: classroom deletion is a soft-delete (archive), not a purge.**
- Deleting sets `meta.archived = true`: the classroom drops off the teacher's active list and **blocks new game creation**, but its resolved board + config stay on disk so existing/historical games still load and rejoin.
- **Game-retention invariant: a game, once created, never breaks because its classroom was deleted.**
- A **hard purge** (reclaim disk) is a separate admin-only operation, gated on "no game references this `instanceId`" (or an explicit force-with-warning).

**Deciding sub-question — RESOLVED by code inspection 2026-06-15.** The question was: does a game *snapshot its resolved board into its own record*, or does the client *re-fetch `/data/i/<id>/` on every load*? Verified against [dataInstance.ts](../../src/utils/dataInstance.ts): the client **re-fetches** — `getDataBasePath()` derives the per-instance path from the URL on every call and the board-data loaders prefix their fetches with it; game state holds no self-contained board copy. There is no runtime fallback to `/data` if the instance path 404s. **Therefore, *with today's re-fetch architecture*, soft-delete is mandatory** — a hard purge of a referenced instance would 404 the board and break rejoin of every in-flight game on it. **CORE-4 changes this:** once game snapshots are self-contained (planned for Phase 1), games stop re-fetching, hard-purge becomes genuinely safe, and soft-delete reverts to the *polite default* (still preferred for historical replay/debugging) rather than a load-bearing constraint. Until CORE-4 lands, the soft-delete + purge-gated-on-no-references rule is load-bearing.

### CORE-4 — Game snapshots must be self-contained (resolved → pulled into Phase 1)

**This closes a spec/implementation divergence, not a new feature.** Decision 5 already states: *"running games keep the board they started with (resolved snapshot per game)"* and the data model says *"games … snapshot their resolved board at creation."* But the implementation does **not** snapshot — verified in CORE-3, the client re-fetches the board from `/data/i/<id>/` on every load, keyed by instance id (not by a pinned resolved version). So today's games are **references, not snapshots.** Two consequences:
1. **Deletion / DR / replay / debugging / migration all reach back into classroom storage** — every one of these is coupled to the instance's live files surviving on disk (the cascade auditor #5 identified).
2. **Decision 5 may not even hold under re-bake**: if a teacher edits and re-bakes mid-game, a running game that re-fetches by instance id would pick up the *new* board — contradicting "running games keep the board they started with." *(To verify against the re-bake/atomic-swap path; self-contained snapshots make the question moot either way.)*

**Decision (audit round 3): make the game snapshot fully self-contained, in Phase 1.** A created game carries its own `{ state, board, movement, effects, metadata }` resolved set (or a content-addressed reference to an immutable, never-rebaked snapshot blob — implementation choice), and stops re-fetching `/data/i/<id>/` after creation. Rationale for pulling it forward rather than deferring: Phase 1 is *already* touching the resolver, game creation, and versioning — this is the cheapest this work will ever be. Defer it and every future feature silently assumes games can reach into classroom storage, and removing that dependency only gets harder. Once done:
- Hard-delete a classroom → existing games unaffected (CORE-3 soft-delete becomes the polite default, no longer load-bearing).
- Disaster recovery → a game is restorable without its classroom.
- The CORE-1 lineage triple becomes a property the game *carries*, not a pointer it dereferences.

This is the single highest-leverage architectural change in the round-2/3 set, and it makes CORE-1, CORE-2, and CORE-3 all more robust at once.

### Promoted invariants

- **INVARIANT — the resolver is pure** (auditor #8). The resolver's only contract is `(stock + config) → (resolved board + validation report)`, with **no side effects**. It already substitutes copies, resolves detours, validates topology, migrates schema, and emits CLEAN files — that is compiler-shaped, and the explicit purity rule is the guardrail that stops future features from quietly pushing *business logic* into it. Anything that needs side effects lives in the server layer that *calls* the resolver, not in the resolver. **Explicitly forbidden inside the resolver** (audit round 4 — a purity rule without a prohibition list is unenforceable): feature-enablement logic, game-rule evaluation, progression-state decisions, player-state inspection, and any I/O beyond writing the resolved output. The resolver transforms a board definition; it must never *reason about a game in progress*. If a future Phase 4 feature wants any of these, that is the signal it belongs in the engine, not the resolver — the same line that cut 4c/4d.
- **INVARIANT — never destroy the last working state** (CORE-2 R4). No replace without a validated successor already on disk.

### Accepted but deferred (documented position, not Phase-1 work)

- **Teacher-copy accumulation / GC** (auditor #3) — Phase 2/3. Rule when built: an *unused* copy is freely deletable (it fills no slot, destroys nothing in play); a copy that *fills a used slot* is not deletable until the slot is refilled. Orphaned-copy GC is a maintenance op, never automatic. Pairs with capacity limits below.
- **Migration source-of-truth precedence** (auditor #4) — already idempotent + verifiable + dry-run (`npm run migrate:check`). Add to the spec: *migration source is immutable, output is deterministic, re-runnable indefinitely.* Precedence at this scale: repo stock + the single live writable working copy are the only sources; multiple boards / volumes / historical backups are explicitly out of scope (single-maintainer assumption — revisit only if that changes). **Define a migration source fingerprint** (audit round 4): the migration records a hash of the exact live-board state it captured, so a *re-run* (after a partial migration, a restore, or a deploy rollback) is unambiguous about what "live" was — same row-hash discipline as CORE-1's `copiedFromStockRowHash`. Without it, "is this the board we already migrated?" has no deterministic answer.
- **Deploy rollback semantics** (auditor #6) — stock **follows the deployed image** (forward *or* back): rolling code v12→v11 reverts the server's stock to v11 on the next on-boot refresh; classroom configs are never reverted. The real edge: a copy made against v12 carries `copiedFromStockVersion: 12`, now *newer* than current stock — **the staleness-hint/schema-diff logic must tolerate `copiedFrom > currentStock`** (treat as "differs," never crash, never auto-reconcile). Add a test for the copied-from-future case.
- **Capacity limits** (auditor #7) — **REJECTED at this scale** (audit round 3, aligning with auditor #3's rejection of enterprise audit-trail machinery). No public signup, no arbitrary uploads, no millions of users — the maintenance burden of copy/classroom/rate/storage caps exceeds the risk for a solo-maintainer, small-school deployment. Documented as a possibility, deliberately not implemented. Re-open only if the deployment model changes to public/multi-tenant.
- **Lifecycle / retention policy** (audit round 4) — quotas are rejected, but "never permanently delete anything" is *also* untenable: archived classrooms, old resolved sets, and backups accumulate forever and eventually dominate storage. Simple policy (Phase 2/3, a *policy* not a subsystem): an **archived classroom with zero referenced games is purgeable** (admin op); **superseded resolved sets** beyond the last-known-good + currently-referenced may be GC'd; **backups** keep last-N plus last-30-days. The retention rule answers "when *can* something be permanently deleted" without re-introducing the quota machinery #7 rejected — distinct concerns: quotas cap *creation*, retention reclaims *dead* state.
- **Disaster recovery** (auditor #11) — one-paragraph story to write into the deploy runbook: **stock** is restored from the deployed image (rebuild + deploy); **classrooms, games, accounts, and instance tokens** all live in the writable volume (`server/data`) and are restored from the Unraid volume backup — there is no other source for them. Implication: the writable volume's backup cadence *is* the classroom/game/account RPO. Cross-references the `deploy.sh` instances-wipe bug (TODO) — until that's fixed, deploy itself is a partial data-loss event for classrooms.
- **Instance-token lifetime / recovery** (auditor #12) — **KEEP** (audit round 3), but framed correctly: these are **operational/administrative tools, not security hardening.** The scenarios (teacher quits, shares a token, loses a laptop, accidentally publishes a token) are ordinary administrative events, not abuse. Build (Phase 3): admin can **rotate** an instance write token (regeneration invalidates the old one), **revoke** = rotate, **ownership transfer** = rotate + reassign `meta.owner`. This is the dividing line from the rejected capacity limits above: reject copy/classroom/rate/storage *quotas* (security hardening for a threat we don't have); keep token revoke/regenerate/ownership-transfer (operational tools for events that will actually happen).

Rationale: catalog/board/insertion/detour edits are all *topology* edits, so "disable Fee Review in tab A + insert Community Hearing in tab B → last save wins" silently destroys one teacher's whole action. This is nearly free now (CORE-2 already carries `configVersion`) and expensive to retrofit once real classrooms exist. Per-instance write serialization still handles file-corruption; the 409 handles lost-intent. *(Promoted out of "deferred" — this is Phase 1/3 work, not someday.)*

At the project's stated scale (schools = dozens-to-hundreds, per BETA_PLAN_V3 scope), this is a non-issue.
